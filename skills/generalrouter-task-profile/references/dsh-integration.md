# DSH Desktop host workflow

The optional GeneralRouter plugin targets DSH Desktop 0.2.1-rc.2 and is distributed as the standard npm package `dsh-generalrouter-0.1.7.tgz`. The planner contract remains `task-profile.v3`; ordinary estimates use `planner_estimated`. The plugin bundles 12 model/effort mappings to the actual ECPA model IDs under DSH provider `easy-cliproxyapi`; the user configures that provider, the model allowlist and supported effort metadata in DSH App. Optional external `routes` override the built-in mapping. No AA slug is assumed to be callable. Quota percentages are read from ECPA without a user-defined grouping layer.

For ordinary subtasks, use the compact dimension definitions and 12-anchor table in `SKILL.md`; the full semantic-anchor JSON and rubric are available when a definition needs clarification. Estimate nonnegative weights summing to one, set `weight_source` to `planner_estimated`, leave `source_task_id` and `calibration_anchor_id` empty, and give the analogy and adjustments in `rationale`. Existing AA reference bindings retain their original source types and exact recorded weights. An absent matching AA sample does not force four nulls; reserve `uncalibrated` for insufficient task information or requirements outside the four-dimensional coverage. The source label supports interpretation and does not establish the accuracy of an estimate.

Reference resources are bundled at fixed versions, with no live benchmark search or automatic periodic update. Updating the package supplies updated resources. Existing saved profiles are preserved, including four-null plans; prepare a new profile in a new session to apply the new instructions. The 12 model configurations, model capability snapshots and default 0.4 composite prior keep their existing roles. Prices, task difficulty and effort resource costs are not new selection criteria in this release.

When `generalrouter_match` is available:

1. Prepare one complete `task-profile.v3` plan using the appropriate source for each task. Pass its JSON string as `profile_json` together with `original_request`. Retain the returned `profile_id`, which identifies the registered plan in this run. Later calls use `profile_id` and optionally `task_id`, without resending the plan or request. The full-profile form remains supported for existing clients; an ID is not permission to alter a registered plan.
2. Read the structured tool status. A setup or allowance error means no worker is ready; do not invent a mapping or bypass the error by directly using a different model tool. Report missing provider or allowlist configuration precisely; the plugin already supplies its standard mappings.
3. For `ready_for_main_agent`, invoke the standard native `subagent` tool with the returned `dispatch` fields exactly. Retain the reservation marker in its prompt. Supply necessary upstream results and artifact references while preserving every original constraint. The concise match response still includes the complete dispatch needed by the worker.
4. Only use a returned supported effort. An omitted `reasoning_effort` means use the selected provider/model default. The recorded AA effort then remains reference metadata rather than a claim about the actual execution.
5. Wait for completion. The plugin associates the child and records the actual host completion event separately from acceptance. Ask the worker for delivered paths, checks actually performed and their results, saved evidence paths, checks not performed, and blockers. Read necessary evidence; make targeted checks if something is missing or contradictory, without automatically repeating the whole suite or adding a reviewer.
6. After execution ends, call `generalrouter_record_acceptance` with `task_id`, `outcome` (`unknown`, `passed`, or `failed`), a concise `summary`, and `evidence` (an array of reference strings). The result is `acceptance_recorded` or `acceptance_already_recorded`. This stores the parent's reported assessment and evidence references; it does not run tests, open evidence, or verify the claim. Worker completion leaves acceptance unknown until assessed. Keep claimed and directly observed evidence distinguishable in the summary.
7. Call `generalrouter_match` with the saved `profile_id` to obtain the next ready task; optionally select `task_id`. Completed dependencies with unknown or passed acceptance may proceed; known failed acceptance blocks new downstream dispatch. Independent tasks may receive separate reservations. Never dispatch one reservation twice or rematch a completed task merely to demonstrate idempotency.
8. Each task's selected provider/model/effort is frozen at its first selection. If dispatch never occurred, release its ticket with `not_dispatched`; the next match may issue a new ticket for that same configuration if still callable and quota-admitted. It does not substitute another configuration. For an actual execution failure use `failed`. A terminal task cannot be reopened: legacy `retry_failed` returns `task_ended`. Further work uses a new appended task below. Tickets do not deduct an estimated quota percentage.
9. Use `generalrouter_report` at completion for observed role/task token counts, linked repair-group totals, timing events and API-equivalent cost. `match`, `status`, and `report` default to concise responses; pass `detail: true` for a concrete candidate or record diagnostic. Full records remain local. Unknown fields remain unknown; the plugin does not reconstruct events emitted before it loaded.

## Appending work without replacing the plan

Call `generalrouter_append_task` with the saved `profile_id` and `task_json`, a JSON string containing one complete ordinary `task-profile.v3` task object. Use a new task ID and existing task IDs for any genuine `depends_on` requirements. This returns `task_appended` (or `task_already_appended` for an identical resubmission) and does not select or dispatch a worker. The original profile, its digest and its ID remain stable; additions are saved separately. Next call `generalrouter_match(profile_id, task_id)` and dispatch the returned selection to a new subagent.

For a repair, also pass `repairs_task_id` referring to an existing completed or failed execution. Include the failed cases, expected/actual outputs, existing artifacts and repair acceptance criteria in the new task's fields. The task object itself keeps the ordinary v3 schema; the repair link is tool metadata. Do not include the repair target in `depends_on`: it is a failed artifact to repair, not a successful prerequisite. Other genuine dependencies remain supported.

New repair tasks are independently estimated and matched once. They may select the same model, and there is no forced upgrade, automatic exclusion, or unlimited-repair policy. Respect the user's scope and stopping conditions. The original task's outcome is not rewritten when a linked repair passes. If an earlier failed dependency is replaced by repaired output, append a new downstream task with the actual repaired dependency instead of mutating the old task's dependency list.

Reports retain individual task costs and related repair-group costs. Historical usage is assigned only when task, reservation, or child-session references establish a unique association; conflicting or absent associations remain unassigned/unknown. Group totals do not turn an original failure into success or establish a same-input comparison: a repair receives failure evidence unavailable during the original attempt.

Normal execution relies on host profile validation and observed completion events. Do not routinely load source code, raw ledgers, full report history, or run the normalizer from the main agent. A concise tool response is not a reason to omit task requirements or acceptance checks. If a response reports a recording problem, use its run/task/operation diagnostic to investigate that issue; do not equate a completed worker with a complete usage record.

Open the actual workspace in DSH before starting the main session. With `projectRoot` left empty, the plugin prefers the project root recorded when that main session was created (`session.header.cwd`). Only when that header is absent may it fall back to the DSH session working-directory service. It does not use the plugin installation directory or the DSH process working directory. A nonempty explicit `projectRoot` can override this path. If no main-session directory is available and no root override was supplied, return the setup error rather than guessing a directory. Once a run is established, child execution, retries and later records retain that run's bound project root; changing directory in the main session or a child does not change this binding.

The plugin registers its bundled planner skill with DSH for sessions across workspaces. A same-name project skill can override the bundled version. Do not ask the user to copy this skill into each new workspace. Shared host configuration is read from `$DSH_HOME/generalrouter/host.local.json`, or `~/.dsh/generalrouter/host.local.json` when `DSH_HOME` is absent. Merge host settings in this order: bundled defaults, shared settings, then `<projectRoot>/host.local.json`. A nonempty explicit `hostConfig` selects the final override file instead. Object fields, including route overrides, merge recursively; project files may specify only changed fields. No host file is required for built-in routing defaults. An absent quota connection produces unknown allowance, not unlimited allowance.

Install through DSH App's Add plugin flow using the absolute path to the downloaded `dsh-generalrouter-0.1.7.tgz` tarball. Existing users update the package through App plugin management and start a new main session. Shared settings, project overrides and usage records remain in place. A same-name project or user skill can still override the package; update that override or back it up and remove it to use the bundled instructions. The package update does not change DSH provider registration, allowlists or effort metadata.

Resolve relative `routing_config`, `rates_file` and `quota_file` paths from the host file that defines each field. A project-specified `quota_file` selects that complete quota configuration; never merge credentials or account identities from shared and project files. Shared connection settings need preparation only once. Keep `state_dir` relative to the current workspace even when it comes from the shared host file. Any absolute state path must remain inside that workspace; otherwise report a configuration error. Each workspace owns its task and usage records. Existing project configuration and skills remain valid overrides; the plugin does not delete or overwrite them. Switching workspaces requires a new main session, not repeated setup.

The standard `subagent` backend must support explicit model selection, and the current session must expose the chosen provider/model in its allowed list. Installing the plugin provides built-in model mappings and the planner skill; it does not enable a provider, set the native allowlist, change the default planner or prove that an app has been delivered.

The first active request reads ECPA when there is no usable recent cache; later refreshes are limited to once per 600 seconds during activity. There is no idle refresh. Reported remaining percentages are preserved without a per-job estimated deduction. Unknown percentages remain unknown and do not block a route by themselves; explicitly reported exhausted applicable windows can exclude it. A fixed parent planner or another client may consume the same account separately, so these observations do not guarantee that an arbitrarily long job will fit within remaining allowance.

Existing user-reported addition, CSV and numerical-repair workflows motivated these changes: a worker could finish with a real defect, an immutable plan could block new repair work, and usage lacked task attribution. Those earlier records do not validate this 0.1.7 change, all candidates, or full acceptance. This update has not undergone development tests, review, validators, compilation/import checks, simulated routing, or model execution. No measured reduction in tokens, cost, quota consumption, or completion time is claimed.
